# Fleet DB 조회와 등록 동시성 개선

- 관련 이슈: https://github.com/sor999/rokin/issues/39
- 결정: [ADR 0007](../decisions/0007-fleet-database-scalability.md)

## 변경 동작

최신 위치, 배터리, 상태는 V10의 `robot_latest`에서 조회한다. Worker는 기존 이력 테이블에
같은 방식으로 적재하며 DB 트리거가 같은 트랜잭션 안에서 투영을 갱신한다. 과거 이력은
수정하거나 삭제하지 않는다. 현재 runtime과 삭제 의도 및 온라인 판정을 하나의 목록
SQL 스냅샷에서 확인한다. 최신 행은 runtime과 종류마다 유지하며 보존 정책은 별도다.

`GET /api/robots`의 배열 응답과 기본 전체 목록은 유지한다. 선택적으로 `limit=1~1000`과
`after=마지막로봇ID`를 전달하면 robot_id 오름차순으로 다음 페이지를 읽는다. 등록된 다른
Fleet의 로봇과 삭제한 로봇은 제외하고, 관리 로봇은 현재 runtime의 관측만 합성한다.
최신 위치와 배터리의 단건 조회 및 명령 접수도 전체 등록 목록 대신 키로 조회한다.
과거 이력 조회 경로는 유지한다.

V11의 Fleet별 행을 생성 상한과 runtime 전환의 배타 락으로 사용한다. 보고는 공유 락과
버전 조건부 UPDATE를 사용해 서로 다른 로봇의 보고를 함께 처리한다. 삭제는 등록 행을
조건부 갱신해 버전을 한 번만 올린다. 전역 ID 중복 방지는 기존 기본키를 유지하고 생성
경쟁의 중복 키 오류는 409로 반환한다. 예전 전역 락 테이블은 지우지 않는다.

Kafka 입력은 등록과 runtime 검증, 관측 갱신, 준비 상태 확인을 같은 SQL에서 수행한다.
이전 관측의 재수신도 UPSERT RETURNING으로 실제 저장된 유효기간을 확인하며, 미래
시각의 중복으로 온라인 상태를 연장하지 않는다. Redis 수신 API의 최종 DB fence는 유지한다.
TTL 캐시는 도입하지 않는다. 이유는 ADR에 기록했다.

내부 관리 목록은 완료된 DELETED 행을 DB 조회에서 제외한다. 종료 보고가 필요한 삭제
중인 로봇은 남기며 공개 등록 목록의 tombstone은 보존한다. delta 프로토콜은 도입하지 않는다.
SSE 연결은 같은 로봇의 동일한 오프라인 관측을 반복 전송하지 않는다. 새 온라인 관측은
억제 기록을 지우고 새 구독은 독립적으로 만료 알림을 받는다. 연결당 기록은 1,024개 이하로
제한하며 이 기록은 명령이나 온라인 판정에 사용하지 않는다.

## 구현 전 검증 시나리오

- 목록은 1대와 20대 모두 SQL 한 번, cursor 페이지 사이 중복 없음
- 중복 event ID, 과거 timestamp와 같은 timestamp의 event ID 순서에 투영 수렴
- 이력 적재 롤백 시 투영도 롤백, V9 이력 backfill 후 기존 Worker INSERT 계속 반영
- 같은 Fleet의 생성 경쟁에서 상한 유지, 다른 Fleet의 등록은 독립적으로 진행
- 서로 다른 Fleet에서 같은 ID 생성 시 하나만 성공하고 다른 요청은 409
- 한 로봇의 보고를 실제 행 락으로 막아도 다른 로봇의 보고는 진행
- 보고 중 runtime 교체는 기다리고, 교체 후 이전 runtime 보고는 거부
- 삭제와 경합한 이전 버전 보고가 tombstone과 증가한 버전을 되돌리지 않음
- 같은 오프라인 관측 반복 억제, 온라인 전이와 새 구독 및 새로운 관측 세대 보존

## 실행 방법과 범위

PostgreSQL 검증은 전용 테스트 DB에서 고유한 임시 스키마를 만들고 정리한다. H2의 읽기
테스트는 이력 기반 테스트 뷰를 사용하며 실제 트리거와 공유 락을 검증했다고 주장하지 않는다.

```bash
PRESENCE_TEST_URL=jdbc:postgresql://localhost:25436/review36 \
FENCE_TEST_URL=jdbc:postgresql://localhost:25436/review36 \
./gradlew test bootJar
```

API 디렉터리에서 Java 25로 실행한다. 기본 테스트 계정과 비밀번호는 이전 공유 상태
검증과 동일한 격리 테스트용 값이며 운영 DB에는 연결하지 않는다. 실제 락 대기는
`pg_stat_activity.wait_event_type='Lock'`을 확인한 뒤 트랜잭션을 해제해 검증한다.

격리 API 2대 환경의 부하 프로필은 기존 baseline을 그대로 사용한다. 3대 로봇, 연결 20개,
120초, 2초마다 정지 명령이다. 개발 DB와 볼륨을 초기화하지 않는다. 변경 전과 변경 후는
의도적으로 다른 소스이며 기존 single/dual 동일 소스 비교 도구의 검사를 완화하지 않는다.
같은 프로필과 Docker 호스트 조건을 확인한 뒤 원본 결과와 DB 누적 통계 차이를 비교한다.
측정 중에는 소스 파일을 변경하지 않는다.

## 배포와 미검증 범위

새 트리거와 기존 이력 backfill은 작업 창에 적용한다. 이력이 클수록 적용 중 쓰기가 대기할
수 있다. Worker가 별도 DB 계정을 쓰는 배포에서는 새 투영의 SELECT, INSERT, UPDATE와
트리거 함수 실행 권한을 확인해야 한다. 현재 Compose는 같은 DB 계정을 사용한다.

구버전 전역 락 API와 새 Fleet 락 API의 생성 요청을 동시에 처리하지 않는다. 이전 API의
관리 요청을 drain한 후 새 버전으로 교체해야 한다. 이 작업은 외부 배포를 수행하지 않는다.
로봇 20대의 목록 쿼리 수와 동시성을 검증하지만 전체 20대의 최대 처리량을 보장하는
시험은 아니다. 고부하 및 장시간 이력 보존 예산은 6단계에서 검증한다.

최종 테스트, 변경 전후 측정과 복구 결과는 검증 완료 후 아래에 기록한다.

## 실행 결과

- API: 테스트 87개, 실패 0개, 기존 Ack 전용 마이그레이션 3개 제외. 새 PostgreSQL 확장성
  8개와 기존 presence 10개, fence 및 Flyway timeout 검증은 실제 DB에서 실행했다.
- Dashboard: 테스트 29개, typecheck와 build 성공.
- Worker: 기존 빌더 컨테이너의 `go test ./...`, `go vet ./...` 성공. 별도 Worker PostgreSQL
  적재 테스트는 반복하지 않았으며 Java의 구버전 INSERT 호환성과 실제 환경 적재로 검증했다.
- ROS: 로봇 13개, Bridge 42개 검증 성공, 별도 환경 전용 3개 제외. compileall 성공.
- 측정기: 기본 24개 중 환경 통합 4개만 제외, 실패 0개.
- 실제 API 2대의 API, Redis, ROS, DB 재시작 및 복구 4개 모두 통과, 127.579초.
  ROS runtime 준비는 기존 Kafka session 만료 대기로 46.690초였다.
- 브라우저에서 Fleet 3대 온라인, 최신 위치와 배터리, robot_1 상세와 WS Connected 및
  명령 버튼을 확인했다. 페이지 요청은 예상한 robot_1, robot_2를 순서대로 반환하고
  잘못된 limit=0은 400을 반환했다. 측정 전 확인용 브라우저를 닫았다.

### 같은 부하의 변경 전후 비교

Docker Engine 29.8.2, aarch64, CPU 11개, 메모리 8,319,369,216바이트의 동일한 호스트에서
실행했다. 두 실행 모두 같은 baseline 프로필과 로봇 시작 설정을 사용하고 10개 기준을
모두 통과했다. API는 2대이며 명령은 각각 58건 모두 접수했다. 측정 전용 원본 파일은
무시된 `tmp/scalability/stage3-before.json`, `stage3-after.json`, `stage3-comparison.json`이다.
변경 전 revision은 174be5b이며 변경 후는 이 작업의 커밋 전 구현 소스다.

DB 왕복 횟수는 약 29.6%, REST p95는 약 31.3% 감소했다. 최신 투영과 일괄 SQL의

측정만으로 DB CPU 비용이 크게 감소했다고 주장하지 않는다. API heap 최댓값도 늘었으며
한 번의 paired 측정과 GC 시점의 영향을 구분하지 않았으므로 메모리 개선으로 해석하지 않는다.
정상 부하에서는 락 경합이 없었다. 다른 Fleet과 다른 로봇의 진행 보장은 별도의 실제
락 경합 테스트에서 확인했다. 결과는 이 3대 로봇 프로필 범위의 관측값이다.

소스 fingerprint는 변경 전 `3fca0d16059031858d2abf188f889816eba533d66e8743a16e65a9e7c35ef248`,
변경 후 `780c2e8ca068f5d7628a354e4c4862071fbdf32a6e2fb1aa629d08453154561c`이다.
측정 구간에는 소스를 바꾸지 않았으며 이후에는 실행 결과 문서를 추가했다.
검증 종료 후 격리 서비스는 정지하고 데이터와 볼륨은 보존한다.

## 검토 후 최종 검증

- V12에서 정적 로봇 partial index를 추가하고 실제 실행 계획에서 인덱스 사용을 확인했다.
- 중복 및 과거 관측의 UPDATE를 생략하고, RETURNING이 비어 있으면 저장된 온라인 상태를
  새 스냅샷에서 읽는다. xmin을 비교해 행 버전이 그대로인지와 만료 판정을 확인했다.
- 로컬 모드는 저장 후 전송 직전에도 공유 소유권과 준비 상태를 확인한다. 실제 PostgreSQL에서
  정상 전송, 저장 이후의 runtime 교체와 삭제에 따른 전송 차단을 검증했다.
- 오프라인 관측 세대 변경은 전송 개수뿐 아니라 새 payload까지 검증한다.
- API 테스트 91개 중 기존 전용 3개를 제외하고 통과했으며 bootJar도 성공했다.
- 제한된 NOLOGIN Worker 역할에서 투영 권한이 없으면 이력도 롤백되고, 문서의 SELECT,
  INSERT, UPDATE 및 함수 실행 권한을 주면 이력과 투영이 함께 적재되는 것을 확인했다.
  이력 INSERT와 sequence 사용 권한도 필요하다. 테스트 역할은 정리했으며 실제 배포 권한은 별도다.
- Java 25와 PostgreSQL 15 서비스를 사용하는 API CI를 추가했다. 첫 실행은 Linux의 나노초
  시각을 테스트용 숫자 JSON으로 변환할 때 정밀도가 손실돼 두 테스트가 실패했다. 실제 API의
  ISO 문자열 계약과 고정된 9자리 나노초 fixture로 수정했으며 해당 회귀 테스트가 통과했다.
- 실제 API 2대의 네 가지 장애 복구 검증은 126.783초에 모두 통과했다.

동일한 baseline 프로필을 구현 커밋 df21fc8에서 다시 측정했다. 기준선과 Docker 호스트
정보가 같고 10개 판정 기준이 모두 통과했으며, 명령 58건 모두 접수하고 이벤트와 완료
Ack 전달률은 100%였다. 이 실행 이후에는 테스트 fixture와 문서만 수정했다.
