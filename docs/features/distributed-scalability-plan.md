# 분산 서버 확장성 개선 계획

- 작성일: 2026-10-30
- 상태: 0~3단계 구현과 검증 완료, 4~6단계 미착수
- 목적: 서버 수를 늘려도 이벤트 전달, 명령 처리, 로봇 소유권의 정합성을 유지한다.

현재 코드에서 확인한 확장 제약을 단계별 작업으로 정리한다. 처리량 한계와 필요한 서버 수는
아직 측정하지 않았다. 아래의 저장소·브로커 구성은 검토안이며, 구현 단계에서 선택 근거와
실패 동작을 ADR로 확정한다. 각 단계는 별도 이슈와 PR로 진행할 수 있도록 완료 기준을 둔다.

## 유지할 계약

- Telemetry의 `event_id`와 Command의 `cmd_id` 기반 멱등성을 유지한다.
- 삭제한 로봇의 이력과 tombstone을 보존하고 ID를 재사용하지 않는다.
- 설정 버전과 runtime 검증으로 이전 실행의 상태 보고·이벤트·명령을 차단한다.
- API/Flyway가 스키마를 소유하며 기존 마이그레이션을 수정하지 않는다.
- 실시간 연결 복구 시 REST 스냅샷과 이벤트를 합성해 최신 상태로 수렴한다.
- ROS 분산 실행을 구현하기 전에는 Fleet당 관리 런타임 하나만 실행한다.

기준 문서: [아키텍처](../../ARCHITECTURE.md), [도메인 계약](../domain/telemetry.md),
[Bridge 소유권 ADR](../decisions/0003-bridge-command-ownership.md),
[관리 런타임 ADR](../decisions/0004-managed-simulations.md).

## 0. 재현 환경과 측정 기준

- [x] API 2대와 로드밸런서, 서로 다른 API에 연결된 브라우저를 갖는 격리 환경을 구성한다.
- [x] 로봇 수, 로봇별 이벤트 주기, 동시 접속자 수, 명령 빈도를 부하 프로필로 기록한다.
- [x] 이벤트 지연, Ack 지연, 명령 오류율, Kafka lag, DB 쿼리 수·지연·락 대기,
  프로세스 메모리와 버퍼 크기를 측정한다.
- [x] 부하 프로필별 지연·오류·복구 시간의 허용 기준을 구현 전 수치로 정한다.

완료 기준: 같은 부하를 반복 실행할 수 있고, 단일 API와 API 2대의 결과를 비교할 수 있다.
데이터와 볼륨을 초기화하지 않고 테스트할 수 있어야 한다.

## 1. API 간 실시간 이벤트·Ack 전달

### 해결한 제약

`TelemetryKafkaListener`와 `RobotAckKafkaListener`는 각각 고정 consumer group을 사용한다.
이벤트는 API 인스턴스 사이에 분배되지만 SSE 연결과 기본 STOMP broker의 구독은 로컬에
있었다. 이벤트를 소비한 서버와 연결을 가진 서버가 다르면 전달되지 않았다.
`TelemetryStreamService`도 연결마다 순차 전송해 느린 연결의 영향이 있었다.

### 작업

- [x] Kafka 소비 후 모든 대상 연결 서버에 전달되는 fan-out 경로를 설계한다.
  외부 STOMP broker relay와 SSE용 서버 간 pub/sub의 장애·재연결 동작을 함께 결정한다.
- [x] 인스턴스별 Kafka group은 단기 대안으로만 평가한다. 전체 이벤트 중복 소비와 DB 조회량,
  종료된 group 정리 비용을 측정하고 영구 적용 여부를 결정한다.
- [x] 연결별 버퍼 상한과 느린 클라이언트 처리 정책을 둔다. 위치 이벤트 병합과 Ack 전달
  정책을 구분하고, 연결 중단 후 REST로 누락 상태를 복구한다.
- [x] 연결 종료·롤링 재시작 시 세션 정리와 재구독을 검증한다. Sticky session에만 의존하지 않는다.
- [x] 전달 경로, 보장 범위, 장애 시 복구 계약을 새 ADR에 기록한다.

완료 기준: 서로 다른 API에 연결한 두 클라이언트가 동일 로봇의 상태와 관련 Ack를 받는다.
한 API가 종료돼도 재연결 후 최신 상태로 수렴하고, 느린 클라이언트가 다른 연결의 지연을
허용 기준 이상으로 높이지 않는다.

결정과 검증: [ADR 0005](../decisions/0005-realtime-fanout.md), [실행 결과](realtime-fanout.md).
인스턴스별 group은 채택하지 않아 별도 비용 실측을 수행하지 않았다. 고정 group과 Redis
전달 경로를 사용한 API 1대/2대의 DB 조회량·메모리·지연을 같은 부하로 비교했다.

## 2. 온라인 상태와 runtime 판정 공유

### 해결한 제약

`TelemetryStreamService`의 인스턴스별 온라인 상태를 제거하고 PostgreSQL의
`robot_presence`를 공통 기준으로 사용한다. 실행 의도와 현재 epoch는 기존 DB 등록이
소유하고, presence는 현재 관측의 유효기간만 제공한다.

### 작업

- [x] 현재 runtime과 마지막 관측 시각의 공통 저장소 및 만료 정책을 결정한다.
- [x] 모든 API가 동일한 준비 상태와 온라인 조건으로 이동 및 정지 요청을 판단한다.
- [x] 이전 runtime과 지연 및 중복 관측으로 온라인 유효기간이 연장되지 않게 한다.
- [x] 공유 저장소 장애 시 명령 거부와 화면의 연결 오류 및 재조회 동작을 정의한다.
- [x] API 재시작, 이벤트 지연, runtime 교체, 저장소 단절을 자동 검증한다.

결정: [ADR 0006](../decisions/0006-shared-presence.md),
실행과 검증: [공유 온라인 상태](shared-presence.md).

ROS 강제 재시작은 기존 Kafka consumer의 session 만료 때문에 약 45초가 필요하다.
API 재연결의 30초 기준은 유지하며 ROS 장애 인계 속도 개선은 5단계에서 수행한다.
DB 쿼리 비용과 갱신 최적화는 3단계에서 같은 부하로 비교한다.

## 3. DB 조회량과 전역 락 경합

같은 관측 세대의 오프라인 반복 전송 억제도 함께 평가한다. 새 온라인 전이와 재구독 복구는 보존한다.

### 해결한 제약

`SimulationRepository.acceptsTelemetry`는 이벤트마다 DB에서 등록·runtime을 확인한다.
`RobotQueryService`는 목록에서 로봇별 최신 위치·배터리·상태를 각각 조회한다.
등록·삭제·상태 보고는 `simulation_registry_lock`의 동일 행을 잠그고, 단일 로봇 조회에도
Fleet 전체 등록 목록을 읽는 경로가 있다.

### 작업

- [x] 등록과 runtime 검증의 캐시 및 일괄 스냅샷을 평가한다. TTL 캐시는 채택하지 않고
  입력의 검증과 관측 저장을 단일 SQL 스냅샷으로 통합하며 수신 API의 DB fence를 유지한다.
- [x] 최신 상태를 이력과 분리해 관리하고 목록은 일괄 조회·페이지 조회로 제공한다.
  투영을 갱신할 때 이벤트 중복과 시간 역행을 처리한다.
- [x] 단일 로봇은 키로 직접 조회하고 반복적인 전체 목록 조회를 제거한다.
- [x] 생성 상한의 동시성 검사는 Fleet 단위로, 상태 보고는 버전·runtime을 조건으로 한
  UPDATE로 분리한다. 전역 ID 중복 방지는 DB 제약으로 계속 보장한다.
- [x] 주기적 목록 조회는 활성 목록과 변경분 조회로 개선할지 평가한다. 삭제 tombstone과
  ID 재사용 금지 기록은 응답 최적화와 별개로 보존한다.

완료 기준: 목록의 쿼리 수가 로봇 수에 비례해 증가하지 않는다. 생성 경쟁에서 상한을
넘지 않고, 삭제·상태 보고·runtime 교체 경쟁에서 오래된 상태가 덮어쓰지 못한다.
변경 전후 쿼리 수·DB 지연·락 대기를 같은 부하로 비교한다.

결정: [ADR 0007](../decisions/0007-fleet-database-scalability.md),
실행 결과: [Fleet DB 확장성](fleet-database-scalability.md).
TTL 캐시와 delta 프로토콜은 평가 후 채택하지 않았다. 입력은 단일 SQL 스냅샷으로 통합하고
수신 API의 DB fence를 유지한다. 최신 투영 조회와 Fleet별 락을 적용했으며 동일 부하의
DB 쿼리는 초기 구현에서 약 29.6%, 검토 수정 후 약 26.7% 감소했다. 검토 수정 후에도
쿼리당 평균 시간과 API heap 관측값은 기준선보다 늘었으며 상세 수치는 실행 문서에 기록했다.

## 4. Worker 부하 제어와 증설·축소

### 진행 상태

이슈 #45에서 구현 및 격리 검증을 완료했다. 첫 PR은 별도 Consumer 및 DB 풀,
예약 상한과 고정 배치 및 세대 검증을, 두 번째 PR은 부하 도구와 운영 설정을 포함한다.
[ADR 0009](../decisions/0009-worker-backpressure.md)와
[실행 결과](worker-backpressure.md)에 소유권과 재처리 및 측정 범위를 기록했다.
DB 600초 중단 후 약 60초에 복구했고 443994건이 전량 저장됐다. Ack 격리 p95는
0.527초, 최대 RSS는 약 99.70MiB였다. 가득 찬 버퍼의 재할당에서 발견한 native
Pause 잔류도 수정했으며 추가 54066건과 이전 정체분 53698건의 저장 및 lag 0을 확인했다.

### 작업

- [x] 배치와 대기 메시지의 상한 및 DB 장애 시 Kafka partition pause/resume 구현
- [x] 텔레메트리와 Ack의 Consumer 및 DB 풀 분리
- [x] 적재 또는 DLQ 전달 확인 후 완료하는 계약 유지
- [x] 할당 세대, 이전 작업 취소, 오프셋 간격과 커밋 실패 단위 테스트
- [x] Worker 증설과 축소, 강제 종료 및 DB 장기 장애 후 전량 재처리 검증

완료 기준: DB 장애 중 메모리가 설정 상한 안에 머무르고, 복구 후 backlog가 수렴한다.
재할당과 재전송 후 `event_id` 기반 중복 적재 방지와 Ack 상태 전이가 유지된다.

## 5. ROS 장애 인계와 실행 서버 분산

### 현재 제약

관리 런타임은 Fleet 전체 등록 로봇을 담당한다. 현재 runtime 등록·epoch는 이전 실행의
보고를 차단하지만 로봇별 서버 배정이나 lease 기반 장애 인계는 제공하지 않는다.
동일 Fleet의 관리 런타임 복제는 현재 지원 범위가 아니다.

### 작업 A: 단일 활성 런타임의 장애 인계

- [ ] lease, 갱신 주기, 만료와 fencing token을 정의한다.
- [ ] 네트워크 단절과 lease 상실 시 기존 실행의 명령 수신·로봇 동작 정책을 정한다.
  DB 보고 거부만으로 기존 실행이 물리적으로 정지했다고 간주하지 않는다.
- [ ] 새 소유자의 실행 허용 조건과 이전 소유자 차단을 검증한다.

### 작업 B: 여러 서버에 로봇 분배

- [ ] 로봇별 소유 runtime 또는 shard와 배정 버전을 영속화한다.
- [ ] 각 관리 런타임이 자신에게 배정된 로봇만 생성·해제하게 한다.
- [ ] Command 라우팅·consumer group·재할당 계약을 ADR 0003과 함께 재설계한다.
  group만 공유해서 명령을 임의의 소유자에게 분배하지 않는다.
- [ ] 한 서버의 추가·종료·장애가 다른 서버의 로봇 이동에 영향을 주지 않는지 검증한다.

완료 기준: 소유권 전환 중 명령 실행 권한이 중복되지 않는다. 이전 소유자의 보고·명령은
차단되고, 새 소유자는 저장된 시작 위치와 초기 배터리로 복구하며 과거 이동을 재개하지 않는다.
분산 실행을 활성화하기 전에 ADR 0004의 단일 런타임 제한을 새 계약으로 대체한다.

## 6. Kafka 용량·가용성과 전체 부하 검증

현재 로컬 토픽 생성은 파티션 3개·복제 계수 1이다. 토픽별 동일 consumer group의 병렬 소비는
파티션 수의 영향을 받으며, 로컬 Compose 구성을 운영 구성으로 간주하지 않는다.

- [ ] 측정한 유입량·lag·처리 시간으로 토픽별 파티션 수와 Worker 수를 정한다.
- [ ] 파티션 증가 시 key의 배정 변화와 로봇별 순서·Command 소유권에 미치는 영향을 검증한다.
- [ ] 운영용 다중 브로커, 복제 계수, ISR, producer 확인 정책과 장애 허용 범위를 설계한다.
- [ ] 이력 보존 기간, 시간별 분할·집계, DB 연결 수와 저장 공간의 예산을 정한다.
- [ ] API·Worker·ROS의 증설과 축소, 브로커·DB·네트워크 장애를 조합해 복구 시간을 측정한다.

완료 기준: 단계 0에서 정한 부하와 허용 기준을 만족한다. 증설 전후 처리량·지연·자원 사용량과
장애 복구 결과를 기록하고, 측정으로 확인한 규모까지만 지원 범위로 선언한다.

## 공통 검증과 작업 기록

각 단계 구현 전에 아래 시나리오를 구체화하고, 완료 후 체크리스트와 측정 결과를 갱신한다.

| 시나리오 | 준비 상태 | 자동 검증 | 수동·환경 의존 검증 |
| --- | --- | --- | --- |
| 정상 전달·명령 | API 2대, 로봇, 서로 다른 연결 | 양쪽 이벤트·Ack 및 명령 판정 일치 | 브라우저에서 이동·정지와 상태 확인 |
| 중복·지연 | 동일 event/cmd ID, 이전 runtime | 중복 적용·상태 역행·과거 명령 실행 방지 | Kafka 재전송과 ROS 동작 확인 |
| 단절·재시작 | API/Worker/ROS 또는 공유 저장소 중단 | 버퍼 상한, 재연결, 버전·소유권 검증 | 실제 서비스 복구와 목록 수렴 확인 |
| 증설·축소 | 실행 중 인스턴스 수 변경 | rebalance·lease 인계·offset 검증 | 다른 로봇의 이동과 Ack 지속 확인 |

- 변경 서비스의 필수 명령은 [검증 컨벤션](../conventions/verification.md)을 따른다.
- 공통 계약 변경은 생산자·소비자와 관련 서비스 전체를 검증한다.
- Docker·브라우저·실제 ROS 검증은 단위 테스트와 구분해 실행 결과를 남긴다.
- 단계별 PR에 변경 계약, ADR, 실행한 검증, 측정 결과, 미검증 범위를 기록한다.
- 외부 배포와 데이터·볼륨 삭제는 이 계획 문서의 작성에 포함되지 않는다.

## 4단계 선행 작업: 명령과 Ack 유실 대비

[영속 전달 계획](durable-command-delivery.md)과 [ADR 0008](../decisions/0008-durable-command-delivery.md)에 따라 API 계약, ROS와 화면 연결, Kafka 3대 장애 검증 순서로 진행한다. 이 작업 이후 Worker 부하 제어를 진행한다.
