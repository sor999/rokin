## 최신 상태와 조회

V10에서 robot_latest를 추가한다. Worker가 기존 이력에 적재하는 같은 트랜잭션의 AFTER
INSERT 트리거가 로봇, runtime, 종류별 최신 관측을 갱신한다. Worker SQL과 공개 이벤트는
바꾸지 않는다. timestamp와 event_id의 사전식 순서로 갱신하여 중복 및 지연 관측에 수렴한다.
기존 이력과 삭제 tombstone은 보존하고, 처음 적용할 때 이력에서 최신 값을 채운다.
트리거 설치와 backfill은 같은 마이그레이션 트랜잭션이다. 이력 규모에 따라 쓰기가 대기할
수 있으므로 운영 적용에는 별도 작업 창을 잡는다. 이 작업에서 외부 배포는 수행하지 않는다.

목록은 이력 스캔과 로봇별 조회 대신 최신 투영과 온라인 관측을 같은 SQL에서 일괄 조회한다.
기존 배열 응답을 유지하고 선택적인 after 및 limit으로 robot_id 기반 페이지를 지원한다.
단일 로봇의 등록은 키로 조회한다. runtime 전환과 삭제 필터는 DB를 직접 확인한다.

## 입력 검증과 캐시

TTL 캐시는 채택하지 않는다. 삭제 및 runtime 전환을 늦게 반영할 수 있고, 이를 피하려면
결국 권위 있는 DB 확인이 필요하다. 대신 Kafka 입력의 등록 검증, presence 저장, 준비 상태
판정을 하나의 SQL 스냅샷으로 묶는다. Redis 수신 API에서는 기존 최종 fence를 유지한다.
DB 장애 시에는 명령과 관측을 로컬 캐시로 허용하지 않는다.

같거나 오래된 관측은 UPDATE를 생략한다. 이 경우 RETURNING이 비어 있다는 이유로
오프라인으로 판단하지 않고 새 SQL 스냅샷으로 저장된 행과 현재 소유권 및 준비 상태를
읽는다. 다른 트랜잭션의 동시 첫 삽입이 이전 스냅샷에 보이지 않는 경우도 처리한다.
새 관측은 기본적으로 단일 SQL이며 이 재수신 경로에는 읽기 한 번이 추가된다.
기본 로컬 모드도 관측 트랜잭션 종료 후 전송 직전에 공유 온라인 판정을 재확인한다.
Redis 모드의 최종 수신 fence는 유지한다.

V12에서 runtime_id가 빈 문자열인 정적 로봇에 partial index를 추가한다. 종료된 runtime
행이 누적돼도 정적 목록 후보를 찾을 때 해당 인덱스를 사용할 수 있다.

## 락 순서와 배포

V11의 Fleet별 행으로 생성 상한과 runtime 교체를 직렬화한다. 상태 보고는 Fleet 행의
공유 락을 얻은 뒤 robot 행을 버전과 현재 runtime 조건으로 갱신한다. 서로 다른 로봇의
보고는 함께 진행하고, runtime 교체는 진행 중인 보고가 끝나기를 기다린다. 삭제는 robot
행의 조건부 UPDATE로 버전을 한 번만 증가시킨다. 전역 robot ID와 runtime ID는 기존
DB 기본키로 중복을 방지한다. global lock 테이블은 이력 호환을 위해 남기지만 사용하지 않는다.

기존 전역 락 API와 새 Fleet 락 API의 생성 요청을 동시에 처리하지 않는다. 배포 시 이전
API의 등록과 삭제 및 runtime 변경 요청을 drain하고 새 버전으로 교체한 뒤 재개한다.
구버전 Worker는 새 트리거와 함께 동작한다. H2에서는 공유 락 검증을 주장하지 않으며
동시성과 트리거는 PostgreSQL 15에서 별도로 검증한다.

## 주기적 목록과 오프라인 전송

내부 관리 목록은 DB에서 DELETED 완료 행을 제외한다. 삭제 중인 항목은 계속 반환해
종료 보고가 수렴하게 한다. 공개 등록 목록은 tombstone을 계속 반환한다. 변경분 프로토콜은
현재 실행 상한 20대와 재시작 복구 복잡도를 고려해 도입하지 않는다.
오프라인 반복 전송은 연결별로 같은 관측 세대만 억제하며, 새 온라인 이벤트와 새 구독은
별도로 처리한다. 이를 온라인 판정의 권위 있는 캐시로 사용하지 않는다.

[트리거](https://www.postgresql.org/docs/15/sql-createtrigger.html).
