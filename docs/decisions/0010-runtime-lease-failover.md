# ADR 0010: 단일 활성 ROS 런타임의 임대와 장애 인계

- 상태: 승인
- 관련 이슈: #49
- 관련 결정: [ADR 0004](0004-managed-simulations.md), [ADR 0008](0008-durable-command-delivery.md)

## 계약

5-A는 가상 로봇의 active-standby 인계다. 로봇별 서버 분배는 5-B 범위다.
Fleet의 기존 DB 잠금으로 lease 획득과 갱신을 직렬화한다. 새 활성 UUID의 session epoch를
fencing token으로 사용하고 12초 동안 유효하게 한다. 갱신 간격은 2초다. 만료된 UUID는
다시 활성화하지 않는다. 프로세스가 새 UUID로 재시작해야 하며 과거 이동은 재개하지 않는다.

활성 서버만 Kafka 명령 Consumer와 ROS 로봇을 생성한다. 대기 서버는 권한 획득만
재시도한다. 로컬 기한은 HTTP 요청 시작 시각에 TTL을 더하고 2초를 뺀 값이며 Linux
CLOCK_BOOTTIME을 사용한다. 늦은 응답은 기한을 늘리지 않는다. 갱신 실패 시 현재 기한까지만
실행하고 만료 시 신규 명령, 이동 갱신과 텔레메트리 발행을 차단한다. ROS 객체 변경은 executor에서 한다.

명령은 runtime UUID와 epoch를 검사한다. ROS 토픽은 runtime별로 격리하고, Kafka 명령
소비 group도 lease epoch별로 분리한다. 이전 Consumer가 남아도 새 활성 서버의 명령을
나눠 가져가지 않는다. 새 group 준비와 로봇 관측 및 RUNNING 보고 전에는 API가 명령을 거부한다.
DB도 만료된 lease의 보고, 온라인 판정과 명령 접수를 거부한다. 명령 접수는 HTTP
제한 3초와 로컬 안전 여유 2초를 더한 최소 5초의 서버 lease 잔여 기간을 요구한다. 단순히 DB 보고만 막고
기존 ROS 실행이 멈췄다고 간주하지 않는다.

각 서버는 독립적인 ROS 영속 볼륨을 사용한다. 대기 중에도 자신의 과거 저널 결과를
회수하며 실행 의도와 진행 중 이동은 결과 확인 불가로 복구한다. 다른 서버의 디스크가
접근 불가하면 해당 결과의 회수는 그 서버 복구 후 진행한다. 전송 사본을 임의로 삭제하지 않는다.

lease는 DB 시계와 클라이언트 시계 속도 차이가 안전 여유보다 작다는 조건에서 사용한다.
DB 시계를 강제로 앞당기는 운영은 금지하며 시간 보정은 점진적으로 수행한다. 일시적인
프로세스 정지와 재개는 BOOTTIME 기한으로 차단한다. 실제 하드웨어의 물리 정지 보장,
동시 디스크 소실 및 무제한 시계 오차는 범위 밖이다.

## 전환

SIMULATOR_LEASE_ENABLED를 API와 관리 ROS에 함께 적용한다. 호환성을 위해 미설정은
기존 단일 런타임 모드이며 기본 Compose는 lease를 활성화한다. V14를 먼저 적용하고
기존 관리 런타임을 모두 정상 종료한 뒤 새 버전을 배치한다. Fleet에서 lease를 한 번
사용하면 레거시 runtime 등록으로 돌아가 실행 권한을 덮어쓸 수 없다.
README는 이번 변경에서 수정하지 않는다.

## 검증 시나리오

| 시나리오 | 준비 | 자동 검증 | 환경 검증 |
| --- | --- | --- | --- |
| 동시 획득 | API 2개와 같은 Fleet | PostgreSQL 실제 잠금과 단일 승자 | 활성 1개와 대기 1개 |
| 서버 종료 | 이동 중 활성 런타임 | 새 epoch와 이전 UUID 거부 | 강제 종료 후 대기 서버 인계 |
| API 단절 | 활성 서버만 갱신 차단 | 로컬 만료와 늦은 응답 거부 | 기존 노드 정지 후 새 서버 실행 |
| 정지 후 재개 | 활성 컨테이너 전체 동결 | BOOTTIME 기준 차단 | 이전 명령과 관측이 새 runtime에 혼입되지 않음 |
| 영속 저널 | 각 서버의 로컬 볼륨 | 재시작 unknown 및 Ack 유지 | 대기 서버의 과거 결과 회수 |
