## 리뷰 절차

1. `git diff` 또는 PR 변경사항과 변경 목적을 확인한다.
2. 변경 영역의 관련 구현, 호출 경로, 테스트와 기존 유사 구현을 확인한다.
3. 프로젝트 컨벤션과 비교하고 변경으로 인한 영향 범위를 분석한다.
4. 실제 문제와 단순 개선 제안을 구분한다.

## 핵심 검토 항목

- **정합성:** 비즈니스 규칙, 예외 처리, null, 경계값, 데이터 무결성
- **동시성:** Race Condition, 트랜잭션, 락 필요성 및 범위, 데드락
- **성능:** N+1, 불필요한 쿼리, 인덱스, 락 경합
- **설계:** 책임 분리, 중복 코드, 추상화, 유지보수성
- **DB:** FK, UNIQUE, CASCADE, Soft Delete와 Hard Delete, Flyway
- **API:** HTTP 상태 코드, Validation, 인증 및 인가, 응답 일관성
- **테스트:** 정상 및 예외 시나리오, 경계값, 테스트 격리, 동시성 검증

## 프로젝트 컨벤션

- 저장소 루트의 `AGENTS.md`와 변경 영역의 기술 스킬을 읽는다.
- 서비스 경계는 [아키텍처](../../../ARCHITECTURE.md), 메시지 식별자와 상태 전이는 [도메인 계약](../../../docs/domain/telemetry.md)을 기준으로 판단한다.
- API는 [spring 스킬](../spring/SKILL.md)을 따른다. Controller의 Repository 직접 접근과 Entity 응답 노출, 트랜잭션 경계, DTO 검증을 확인한다.
- Worker는 [go 스킬](../go/SKILL.md)을 따른다. `event_id` 기반 멱등 적재, 제한된 동시성, 적재 실패와 재전송 처리를 확인한다.
- ROS2는 [ros2 스킬](../ros2/SKILL.md)을 따른다. Node와 순수 상태 로직의 분리, `cmd_id` 기반 중복 명령 처리, Command/Ack 상태 전이를 확인한다.
- Dashboard는 [nextjs 스킬](../nextjs/SKILL.md)을 따른다. 클라이언트 비밀값 노출, 연결 단절과 재연결, 오래된 응답과 최신 상태의 역행을 확인한다.
- 공통 계약 변경은 생산자와 소비자, Flyway와 Worker SQL의 호환성까지 확인한다.
- [검증 컨벤션](../../../docs/conventions/verification.md)을 따른다. API 기본 테스트는 H2와 Java 25를 사용하며 PostgreSQL Testcontainers를 일괄 강제하지 않는다.

## 리뷰 원칙

- 변경 코드뿐 아니라 관련 기존 구현도 확인한다.
- 프로젝트 컨벤션을 일반적인 취향보다 우선한다.
- 실제 버그, 설계 개선, 스타일 제안을 구분한다.
- 불필요한 최적화와 과도한 추상화를 강요하지 않는다.
- 이미 반영되었거나 작성된 리뷰를 중복하지 않는다.
- 근거 없는 문제를 만들어내지 않는다.
- 기존 구현과 다른 부분은 이유를 확인한 후 개선을 제안한다.
- 컨벤션 위반은 기존 코드 또는 명시된 프로젝트 규칙을 근거로 판단한다.

## 출력 형식

각 리뷰는 다음 형식으로 작성한다.

- **우선순위:** 필수 / 권장 / 선택
- **위치:** 파일명 및 라인
- **문제:** 발생 원인과 실제 영향
- **개선:** 구체적인 수정 방향
- **리뷰 코멘트:** GitHub에 바로 작성할 수 있는 정중하고 간결한 한국어

치명적인 문제부터 출력하며, 문제없는 부분은 불필요하게 지적하지 않는다.

리뷰 요청은 분석과 코멘트 작성까지 수행한다. GitHub 리뷰 게시는 사용자가 요청한 경우에 수행한다.
